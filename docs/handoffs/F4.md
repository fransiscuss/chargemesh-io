Status: complete. Implementation commit: `6e5d4ed`, pushed to `main`.
[CI passed](https://github.com/fransiscuss/chargemesh-io/actions/runs/35307282237).
This handoff is published in the documentation commit immediately after implementation.

## Delivered

- `apps/gateway/src/recorder/eventBuilder.ts`: pure `buildEvent(ctx, parsed)` mapping
  to the §3.3 `OcppEvent` envelope (without id). Reuses the Router-resolved
  `ctx.action`/`ctx.latencyMs`, so CALLRESULT/ERROR correlation and latency come
  from `PendingCalls` with no re-resolution. CallError payloads are kept as
  `{code, description, details}`.
- `apps/gateway/src/recorder/validator.ts`: `createValidatorInterceptor()` async
  interceptor. Validates CALL `req` and correlated CALLRESULT `conf` payloads
  against the versioned OCA schemas (per-version validator cache). A CALLRESULT
  with no correlation is recorded with `action=null`, `valid=false` and an
  `unknown_correlation` error; parseable CallErrors are valid; unparseable input
  is `parse_error`.
- `apps/gateway/src/recorder/batchWriter.ts`: generic bounded `BatchWriter`
  (flush every 1s or 200 rows, 10k queue cap). Overflow drops the oldest, rejects
  its promise, increments the counter (`createDropCounter()` backs the
  `recorder_dropped_total` metric) and logs a warning. Failed batches retry with
  exponential backoff (200ms → 5s). A next-tick eager drain resolves stragglers
  promptly so `pipeline.flush()` never waits a full interval; under load the
  200-row trigger preserves batching. `flush()` drains everything; `close()`
  stops timers and drains.
- `apps/gateway/src/recorder/recorder.ts`: `createDbSink` (multi-row insert into
  `ocpp_messages` returning DB ids, plus per-charger `last_seen_at` advance),
  `createRecorder` (resolves `ctx.recorded` with the DB-assigned id),
  `createBusPublisher` (publishes after the DB id is assigned — no provisional
  ulid; documented in code), and `createRecording` wiring
  validator → recorder → busPublisher plus writer/bus/flush/close.
- `apps/gateway/src/recorder/eventBus.ts`: `EventBus` interface
  (`publish`, `subscribe(filter, handler) → unsubscribe`) with `InProcessEventBus`
  fan-out. Filters by charger/action/source; unsubscribe removes; a throwing or
  slow subscriber never blocks the others.
- `apps/gateway/src/recorder/connections.ts`: `ConnectionTracker` writing
  `connections` rows on open and close for charger and upstream legs, maintaining
  `chargers.connected` (charger leg) and `last_seen_at`. Tracking is best-effort
  and never fails upgrades.
- Wiring: `index.ts` production gateway uses
  `Pipeline([], [validator, recorder, busPublisher])` with a `ConnectionTracker`;
  `server.ts` accepts optional `recorder`/`connections` hooks, records both legs
  on upgrade (close-code listeners, errors logged only), and shutdown flushes
  recorder → pipeline → recorder. `pipeline.ts` `FrameContext` gains optional
  `validation` and `recorded` fields; F3 sync/async semantics untouched.

## Extension points and decisions

- Malformed-frame envelope settled (spec Open question): `msgType`/`uniqueId`/
  `action` are nullable in the internal `OcppEvent` and the DB row; `raw` always
  holds the original bytes; `payload` is null; `valid=false` with errors.
  External (REST/SSE/gRPC) representation still to be fixed in F10/F13; the
  nullable internal shape is the starting point.
- Publish happens after the DB id is assigned via `ctx.recorded`; no provisional
  ulid is used.
- Unmatched CALLRESULTs (e.g. correlation expired after 120s sweep) are recorded
  with `action=null`, `latencyMs=null`, `valid=false` (`unknown_correlation`).
  F11 `response_timeout`/`schema_invalid` rules should be aware of this flag.
- Charger-source frames record `upstreamId=null`/`upstreamRole=null` (F3 Router
  semantics preserved); association with the primary lives in `delivery`.
- `BatchWriter.drain` retries failed batches indefinitely, so `flush()` (and
  therefore shutdown) waits for the DB to recover rather than dropping records.
  If shutdown-hang behaviour needs bounding later, that is an F5/F14 concern.
- The pg vs PGlite drizzle surfaces share runtime call shapes but diverge in
  deep result types; sink/tracker normalize with one cast each. PGlite tests run
  the real production migrations.
